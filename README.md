# setlist-controller

A browser setlist controller for Ableton Live, for a band's Sunday playback. A local server on the playback Mac talks to Live through AbletonOSC and serves an offline web app to the leader's iPad and the band's phones.

The spec lives on setlist-controller#1.

## Development

You need Node 24 or later and pnpm. Install the dependencies once:

```sh
pnpm install
```

The fake Live stands in for Ableton Live with AbletonOSC, so the app runs end to end on a Mac without Live. Run each of these in its own terminal.

1. The fake Live. It listens for OSC on port 11000 and replies on port 11001, as AbletonOSC does. It holds a two-song demo set at 120 BPM in 4/4, stopped at beat 0. Play it from the leader page, whose URL the server prints at start:

   ```sh
   pnpm dev:fake-live
   ```

2. The server. It sends OSC to port 11000, receives on port 11001, and serves the web app on port 8080. It checks for Live every second, and reads the set each time Live connects, so the two can start in either order. At start it prints the leader page's URL, which carries the install's leader secret:

   ```sh
   pnpm dev:server
   ```

   The dev server writes its lateness log to `dist/dev-cue-lateness.log`, not to the installed server's log, and `pnpm dev:server --lateness-log <path>` sends it elsewhere. `pnpm lateness --log dist/dev-cue-lateness.log` summarizes it, and the format and the summary are in `docs/install.md`, section 4.

3. The web app, with hot reload, on http://localhost:5173. It proxies the WebSocket to the server on port 8080:

   ```sh
   pnpm dev:web
   ```

The server reads the leader's MIDI foot pedal from every MIDI source on the Mac, and maps it with the pedal config file, by default `~/Library/Application Support/setlist-controller/pedal.json`. Give it another file with `pnpm dev:server --pedal-config <path>`; the format is in `docs/install.md`, section 5. With no file, or no pedal, the server runs as usual and the pedal does nothing. With no pedal plugged in, the setup screen's MIDI monitor stays empty.

The server reads the connection targets, such as ProPresenter, from the connections config file, by default `~/Library/Application Support/setlist-controller/connections.json` beside `pedal.json`. Give it another file with `pnpm dev:server --connections-config <path>`; the format is in `docs/install.md`, section 7. The server reads the file once at start, so restart it after a change. With no file, no target starts and the server runs as usual. A section for a kind of target the server does not know, or one the target rejects, disables that target alone: it shows as "Not configured" with its problems, and every other target starts. A file that is not JSON, has no `targets` object or cannot be read starts no target at all, and its one problem shows in place of the rows.

The chart view takes each song's chart from the set manifest, one JSON file holding each song's title, stems key, chart key and chart text, by default `~/Library/Application Support/setlist-controller/set-manifest.json` beside the leader secret. `pnpm build-set` writes it on every build, as [Building the Sunday set](#building-the-sunday-set) says. Give it another file with `pnpm dev:server --set-manifest <path>`; the format is in `docs/install.md`, section 8. The server reads the file at start, on Refresh and whenever the file changes, with no restart, and serves the charts at `/api/charts` to every page. Each snapshot carries a chart revision that rises when a read finds the file changed, and a page fetches the charts again when it does, so an open page shows the new chart with no reload. With no file, every song shows no chart text; a file that is not a manifest shows none either, and the server logs its problem. Tests always pass a path inside the worktree, so no test reads the home folder.

The Charts connection target holds each song of the set against its chart in the set manifest, so a heading that does not match shows before the band needs the chart view. The server adds a Charts row to the producer page's Connections panel and to the setup screen whenever it has a set manifest path, which production always does, with no section in the connections config. Its pre-service check runs on every trigger a target's check runs on, such as Refresh and a changed set, and whenever the manifest changes. Cannot match lists each locator with no matching heading in its song's chart, as `<song>: <locator>`, by the name rule and the occurrence rule every target uses, and never Count Off, Pad, Pad Out or End. Problems lists a set manifest that is missing or cannot be read, alone, or else each song with no chart: an untitled song, a title the manifest does not hold, or a song with no chart text. Notes lists an empty chart key (the stems key is used), chart text with no chords in brackets, each line the chart view drops, such as a `TRANSPOSE KEY` line or a line before the first heading, and a heading no locator reaches. As with every target's check, no band page receives it. Charts follows no cue: it is always online, its lateness is never measured, and Arm, Disarm and Fire again do nothing for it.

The server reads the playback Mac's power with `pmset -g batt` every 10 seconds, and every page's snapshot carries it. A Playback Mac row on the producer page's Connections panel and on the setup screen holds its pre-service check, which fails while the Mac runs on battery at any charge, so a kicked cord is caught before the set starts, and passes again once it is back on mains power. The leader page, the producer page and the setup screen show a banner with the charge at the top of the page, under the producer's message and the Reconnecting banner, while the Mac is on battery at 80% or less, amber, and red at 30% or less or when no charge is read. The banner goes as soon as the Mac is back on mains power, and a brief unplug above 80% shows none. Dismiss takes it off that page, so the controls under it are in reach, until the warning changes: it shows again when amber turns red, and when the Mac goes back on battery after mains power. A reload shows it again, and the Playback Mac row still reports the battery. The band's view-only page never shows it. A machine where `pmset` cannot run, or prints what the server cannot read, reads as not known: its check passes with a note, and no banner shows. Like Charts, the row follows no cue, and Arm, Disarm and Fire again do nothing for it.

Every page but the setup screen says hello to the server on each connection: a client ID it makes once for its role and keeps in the browser's storage, the name the device goes by, and its battery. The name is the one typed in the Device name field, else the device's role, Leader or Producer, else the band part picked, else View only. The producer page's Devices panel, under Connections, and the setup screen list every device in the order each first said hello, by its name, its role, Online or Offline with the time it was last seen, and its battery, or Battery not reported where the browser gives none: Safari has no battery reading, and Chrome gives one only over HTTPS, so a phone on the stage network over plain HTTP reports none. A device that leaves stays listed Offline until it comes back, the producer presses Clear offline, or the server restarts. Reload on another online device's row reloads that device's pages alone; the producer's own row has none. Only the producer page sends Reload and Clear offline, and the setup screen lists the devices with neither. A browser keeps one client ID for each page role, so the producer page and a leader page in one browser are two devices. Two tabs of one page in one browser are one device: Reload reloads both, and a name typed in one tab reaches the other.

The producer page's Message the band panel, under the Devices panel, sends a message to the band's devices: the producer picks All devices, View-only devices, or Chosen devices from the Devices panel's list, then taps a quick message (Repeat chorus, Repeat bridge, Hold after this song, Watch leader), which sends at once, or types one and presses Send. Each device it reaches shows it in a white banner held to the top of the page, with Dismiss. A message to All devices reaches every page but the producer pages, which list it instead; a producer page picked under Chosen devices shows it, until a newer message to All devices replaces it there too. A device shows one message at a time, the newest that reached it, and the server sends it again on every connection, so it shows again after a reload or a dropped connection. A message to All devices or View-only devices also reaches a device that first connects after it, and one to chosen devices reaches a chosen device that was offline when it comes back. Dismiss hides the message on that device, in each of its tabs and across reloads, until a newer message comes. A Dismiss on one page leaves the message on a page of another role in the same browser, so a Dismiss on a chosen producer page leaves it on a leader page there. Clear messages takes every message off every device. The panel lists each active message, newest first, with who it was sent to and when, and the Devices panel names the message each device shows, offline devices included. A page keeps its Dismiss to itself, so the producer page cannot tell which devices dismissed it. Only the producer page sends a message or Clear. The server keeps the messages in memory alone, so a restart clears them.

To see the built app instead, run `pnpm build` and open http://localhost:8080, which the server serves from `dist/web`.

The setup screen is `/setup`, such as http://localhost:8080/setup. The operator checks it on the playback laptop before rehearsal: it shows whether Live is connected, where the set is, the warnings about the locators, the foot pedal's config and MIDI monitor, the connections config ("Connections config loaded.", "No connections config." or "Connections config rejected.", with the file's path and any problem with the file) and each connection target as Online, Offline or Not configured, with its pre-service check or the problems that disabled it, and QR codes for the leader page, the producer page and the view-only page. Its Refresh reads the locators from Live at once after an edit, as the leader's does, and works only on the laptop itself. The QR codes, the foot pedal's config and MIDI monitor, and the connections config and the targets' checks open only on the laptop itself; any other device gets the page without them, and no band page ever receives the pedal's status or a target's check.

When Live stops answering for a few seconds, every page shows "Live not connected" in place of the song. Stop the fake Live to see it. Start it again and the pages return, since the server registers its listeners again when Live comes back.

A page that loses the server, such as a phone that drops Wi-Fi, tries again on its own every 2 seconds or sooner, and at once when the device wakes, with no reload. It keeps showing what it last had until the server answers, then shows the current state.

The URL sets the role, with no login. The default path, such as http://localhost:5173/, is the view-only page for the band's phones and FOH: it shows where the set is and never controls Live. The view-only page opens on a "Part" select, with "No part", Keys, Guitar, Bass, Vocals and Drums. A part opens the chart view in place of the now-playing panel and the setlist, and "No part" brings them back. The device keeps the part in the browser's own storage, so the page opens on the same part after a reload; a device that cannot store, such as Safari in private mode, keeps it for the visit only. Each part opens on its default display: Keys, Guitar and Bass on "Chords over lyrics", Vocals on "Lyrics only", and Drums on "Section map", each block's name and bar count with no lyrics and no chords. A "Display" select after the "Part" select changes it to any of the three, and the device keeps the display for each part in its own storage, so a reload opens the part on the display it last had, and another part on its own. The chart view shows the current song as one block per locator, in played order, so a section repeated in Live shows each time, the Count Off and the End included. Each block shows the section's name and its bar count, counted in 4/4 from the locators, while the current block shows Live's own count, as the now-playing panel does. Under its name, in "Chords over lyrics", each block shows its section's chords over its lyrics, each chord over the syllable it falls on, from the song's chart in the set manifest, matched to the song by the title on its Count Off locator with the name rule. In "Lyrics only", each block shows the same lines as words with no chords, keeps the chart's notes, and drops a line of chords alone, so a block of chords alone, such as an Intro, shows only its name and bar count. The nth section of a name takes the nth heading of that name in the chart, and a section past the last heading of its name takes that last one, so a third Chorus in a chart with two CHORUS headings shows the second. Count Off, Pad, Pad Out, End, a heading with no text and a section the chart has no heading for show the name and bar count alone, and a song with no chart in the set manifest shows "No chart for this song" over its blocks' names and bar counts. Chords show in the stems' key: each chord's root and slash bass move from the chart key to the stems key, both from the set manifest, named with sharps or flats as the stems key takes them, and the rest of the chord, such as m, 7, maj7, sus4 or add9, shows as typed. A minor key moves through its relative major, so a chart in Em shows unmoved for stems in G. A chart with no chart key, a song with no stems key, or a key the chart view cannot read as a note name shows its chords as typed. In "Chords over lyrics", a "Chord names" select after the "Display" select shows the chords as "Letters", the default, or as "Nashville numbers". Numbers count from the stems key's tonic, or the chart key's for a song with no stems key, a minor key from its minor tonic against its own scale. They keep the chord's suffix, such as 6m, 4maj7 or 1/3, and mark a root outside the scale with a flat or a sharp, such as b7 or #4. Each song with a chart also gets a "Capo" select under its title, from "No capo", the default, to 7: a capo of n shows each chord n semitones lower, as the shape key spells it, with a "Capo n" label on that song, such as "Capo 3" over a song in G shown in E shapes. Numbers ignore the capo. The device keeps the chord names, and each song's capo by its title, in its own storage, so the chart view opens with the same chord names and capos after a reload. The current block is highlighted and scrolled to the top of the page, and follows the playhead and a jump at once; a waiting jump and the loop are marked as in the setlist. Over the blocks, a pinned strip stays at the top of the screen with the next section and the bars until it starts, counted down from Live's own bar count, such as "Next Chorus in 6 bars". It shows "Loop" with no countdown while the loop is on, the next song's title and first section in a song's last section, and no countdown in the last section of the set's last song with no End, where it reads "Last section". The current block scrolls to just under the strip, so the strip never covers it. A "View" select after the "Display" select picks "This song", the default, which shows the song the playhead is in and changes song when the next song starts, or "Whole set", which shows every song one after the next, in set order, with the same strip and highlight, the current block still scrolled to just under the strip. A "Font size" select after it scales the chart's text in five steps, "Small", "Medium", the default, "Large", "Larger" and "Largest", and leaves the selects at their own size. The device keeps the view and the font size in its own storage, one each whatever the part, so the chart view opens on the same view and font size after a reload. On a device's first open, the view-only page shows a tip after its selects to set Auto-Lock to Never for the service, and Screen timeout to its longest on Android, since a phone that locks mid-song loses the chart; the device keeps that the tip was shown, so it is gone after a reload. The page cannot keep the screen on by itself: the Screen Wake Lock needs HTTPS, and the server serves plain HTTP. Between songs it keeps the song just played. The chart view connects as a viewer, on the same connection as every view-only page, so it never controls Live, and no select sends anything to the server. Every page shows each song's end toggle, "Stop at end" or "Continue into next song". On "Stop at end", the server stops Live when the playhead reaches the song's End; on "Continue", playback rolls on into the next song. A song whose End sits on the next song's first locator, as an overlap or a pad builds it, starts on "Continue into next song"; every other song, and the last song, starts on "Stop at end". The leader page is `/leader/<secret>`, such as http://localhost:5173/leader/<secret>, where `<secret>` is the install's leader secret, made on the server's first start and kept in `~/Library/Application Support/setlist-controller/leader-secret`. `pnpm dev:server` prints the leader page's URL at start, and the setup screen's leader QR code holds it. `/leader` alone, or with a wrong secret, never controls Live: with no secret it is the view-only page, and with a wrong one the server refuses its connection. The producer page is `/producer/<secret>`, where `<secret>` is the install's producer secret, made, kept and replaced the same way in `~/Library/Application Support/setlist-controller/producer-secret`, beside the leader's and independent of it. `pnpm dev:server` prints the producer page's URL at start, and the setup screen's producer QR code, next to the leader's, holds it. The producer page is the leader page, with every leader control, plus a Connections panel; with no targets configured, the panel says no connections are configured. Each target's row shows whether it is armed, disarmed or paused, and why it is paused: Arm makes it follow the set, cue by cue, and Disarm stops it. Every target starts disarmed. A change made by hand at the target itself pauses it ("Paused by hand") until the producer arms it again. The leader's Fade out pauses every armed target that follows the track timing ("Paused by Fade out"), and the next song's Count Off, where the music comes back, arms each of them again and hands it that Count Off. A song with no Count Off does the same on its first section, where the music comes back at once, and hands each of them that section's cue. A target that opts out of the Fade out stays armed. A paused target gets no cue, and gets nothing it missed once it is armed again. Beside Arm and Disarm, each row has Fire again, which sends that target alone the cue for the section the playhead is in now, and the target's own manual buttons, such as clearing the slides, which run on that target. Both work whatever the target's arm state and leave it as it was, so neither arms nor pauses it. Both are disabled while the target is offline, and Fire again does nothing between songs. The page draws the buttons a target declares, so a new target needs no change to the page. A target can also ask the producer to pick one of a list for the set, and the page draws that too: ProPresenter's row has a Playlist select listing the playlists ProPresenter holds, read again when it comes online and on Refresh, and a line naming the picked playlist, or "No playlist picked". The pick is kept per set, by the set's songs and titles as the server reads them from Live, in `propresenter-picks.json` beside the connections config, so it survives a restart, and a set the server has not seen asks for a pick again. Armed, ProPresenter triggers the first slide of the group named as each section in the song's presentation in that playlist, by that slide's index in the presentation, matched by the same name rule as the check below. Then the server triggers each later slide of that group itself, on an even split of the section's bars: with n slides over b bars, slide k goes k × b / n bars into the section, rounded to the nearest bar line (a half rounds up), at least a bar after the slide before it, or on beats in the same way when the group has more slides than the section has bars. The last section of a song with no End runs to the next song's first locator, so its slides split over those bars in the same way; the last song's, with no song after it, has no end and shows its first slide alone. While Live plays forward, each lyric slide goes up a lead ahead of its beat, so the words are on the screens before the line: 2 beats unless ProPresenter's section of the connections config sets `leadBeats`, where 0 sends each slide on its beat. A song whose words do not fit that split, or whose section has no group of its name, takes per-song exceptions in the slide timing file, `config/slide-timing.json` in this repository beside the stem map: an entry names a section of the song and which one of its name it is, and gives `changes`, the bar of each slide change after the first counted from the section's start, decimals allowed, which replace the even split, or `group`, the position from 1 of the group the section shows in the presentation's group order, as ProPresenter lists them, or both. The server reads the file with the set and the presentations, and again on Refresh, so an edit takes effect from the next Refresh with nothing to restart, and a missing file means no exceptions (docs/install.md, section 7). While Live's loop is on, the section's first slide also goes up the lead before each wrap, and the next section's never does while the loop holds. When a song plays on into the next, its end toggle on "Continue into next song", or a song with no End, which always plays on since Live never stops there, the next song's first slide goes up the lead before its downbeat too, and that song's End, when it falls inside that lead, sends nothing, whether the playhead plays into it or Next on the song's last section jumps there: no clear and no End or Ending group. When the next song's first slide has not gone by then, as after a Fade out or a pause at its send time, that End sends the slide at once in place of a clear, and the next song's downbeat does not send it again. An End, or a section that clears, that Live reports only after the slide for a place past it went sends nothing too, so that slide is not blanked and sent again. The server predicts when the playhead reaches the slide's beat from Live's last report of the playhead and its tempo, and a report that moves the playhead more than a beat from where it was predicted, such as a drag at the laptop or a tempo change, moves the slide change with it. A clear stays on its downbeat, with no lead. Stop, a jump request, the loop going on or off, and a Fade out drop a slide change not yet sent. The leader's Loop press drops it at the press, before Live reports the loop, so a press in a section's last beats never lets the next section's first slide go up. A slide sent early is not sent again on its beat, and a change that comes due while ProPresenter is paused is dropped. Clear slide, ProPresenter going offline, a slide pressed by hand and Disarm each forget that a slide went early, so its beat, the next section's downbeat or a song's End sends as it would have. Next slide and Previous slide keep it, so the slide a press moved to stays up through that beat. Fire again before the beat of a slide sent early sends that slide again. A jump landing, Play from start, a start in the middle of a section, a drag back inside the section playing and Fire again send the slide for where the playhead is, and the leader's Stop and a jump drop a slide change not yet sent. A jump landing, Play from start or a count-in that lands inside a slide's lead sends that slide at once, as a drag back there does, so Next to a song's End inside the lead of the next song's first slide sends that slide and no clear. A section with no group of its name shows slide 1 of the presentation when it comes before the song's first section with a group, such as a Count Off or an Intro with no group, and otherwise clears the slide layer on its downbeat, so the last slide never stays up through a Turnaround or an Interlude. A song it cannot match triggers nothing. The nth section of a name in a song triggers the nth group of that name in the presentation's order, so Worthy Of It All's second Chorus triggers its second Chorus group, and a section past the last group of its name triggers that last group. Fire again, a jump and a loop wrap trigger the group for the section the playhead is in, at the slide for the playhead's position, so a loop on the second Chorus triggers the second Chorus group again. A song's End triggers the first slide of its group named End, or else of its group named Ending, unless the song has an Ending section of its own, whose cue has triggered the Ending group already, or its last section clears, as an Outro or a Pad Out with no group does, so the screen is already blank. An End with no group to show clears the slide layer, so the last line never stays up after the music and the Ending lyrics never come back after it: a song with neither an End nor an Ending group, a song with an Ending section of its own and no End group, and a song with no End group whose last section clears. A song whose playlist item is on an arrangement other than Master triggers nothing, since ProPresenter does not tell the server that arrangement's slides, so an index would land on the wrong slide. A trigger ProPresenter refuses, such as a 404 for a slide removed after the read, is logged with the song, the section and the answer, and the row says so in a line such as "Trigger refused for There Is Freedom, Chorus: ProPresenter answered 404.", until the next trigger is sent or a press succeeds. The select is disabled while ProPresenter is offline, and while the server has read no set from Live, when the line under it says "No playlist can be picked until the set is read from Live." in place of naming the pick. ProPresenter's own buttons are Next slide, Previous slide and Clear slide, which act on whatever presentation ProPresenter has active, with or without a playlist picked. After a clear, a section's or Clear slide's, ProPresenter has no presentation active, so Next slide shows the slide after the last slide shown and Previous slide shows the last slide shown again, each by its index in the presentation last triggered. Before any slide has shown, Next slide and Previous slide have nothing to move, and neither does Next slide on the last slide: the row says so in a line such as "Pressed Next slide: nothing to move.", and ProPresenter stays online. Every press logs one line to the server's output with the button, the request sent, what ProPresenter answered and how long it took. A press's line opens with "Pressed", so it never reads as the status stream's "Next slide:" line. Any other answer that is not a success shows in the same line with its status, a press that succeeds clears it, and so does the next trigger a cue sends. While ProPresenter is online, its row also shows the current slide's text and the next slide's, from ProPresenter's status stream, as "Current slide:" and "Next slide:" lines with each slide's lines joined by " / ", and "(no words)" for a slide with none, such as a media slide. The row shows the live slide's text as soon as the stream opens, at the server's start and after a reconnect, and then the last text the stream reported, since ProPresenter does not report every slide change, and none after a clear. A Clear slide press that ProPresenter accepts blanks the slide text at once, since some clears bring no word from the stream. A slide pressed by hand in ProPresenter pauses it ("Paused by hand") until the producer arms it again, while its own triggers, slide changes, clears and buttons never do. Since the server moves every slide, a press of another slide of the same group pauses ProPresenter too, so its presentations must carry no Go To Next timers (`docs/install.md`, section 7). A clear the server sends blanks the slide text at once, as a Clear slide press does, and expects no slide, so a slide pressed by hand after it pauses ProPresenter. A line about a slide button press comes after the slide text, and neither hides the other. A dropped stream shows ProPresenter offline, and the server reconnects on its own and opens the stream again. A stream that sends nothing for 10 seconds while ProPresenter still answers, as a ProPresenter that has run for a day or more can, keeps ProPresenter online, since slide changes do not need the stream: the server opens the stream again after 10 seconds of silence, then after 20, 40 and 60, and every 60 after that, until ProPresenter's heartbeat comes back, and only a ProPresenter that stops answering goes offline. While the stream is quiet, the row keeps the last slide text with the line "slide text not live, status stream quiet" under it, and the check names "ProPresenter's status stream is quiet: quit and reopen ProPresenter before the service." first under "Problems:". When ProPresenter comes back online, still armed, with Live still in the section whose slide change came due while it was offline, the server sends the slide for the playhead once, as Fire again does; nothing else it missed is sent. Once a measured cue has reached a target, its row shows how late the cues reach it, as "Late 250 ms, median 240 ms" for the last cue and the median of the last 50, by nearest rank, the same median `pnpm lateness` prints, and, for a target that reports acting on its cues, a second line such as "Acted on 370 ms, median 360 ms"; each of those cues also gets a line in the lateness log (`docs/install.md`, section 4). A target the connections config file disabled has a red "Not configured" row with its problems and no buttons, and a problem with the file itself shows in place of the rows. Each target's row shows its pre-service check: before the service, each target checks the set against its own file and lists the songs and sections it cannot match under "Cannot match:", as the target words them, or says every song and section matches. Last, in grey, under "Notes:", it lists what a matched song or section does that the producer may want to know but need not fix; a check with notes and nothing it cannot match still says every song and section matches. Whatever keeps a target from checking the set, or is otherwise wrong with its own file, such as no playlist picked, or two lights cues with one label, of which one never fires, or a cue list that is not in the show file, is listed under "Problems:", before the songs and sections it cannot match, so a problem never reads as a name that did not match. A target that matches no names checks its own device instead, and lists what is wrong with it and what it reports, such as an ATEM input the config names but the ATEM does not have, or one that is one of the ATEM's own sources, such as Color Bars or a media player, rather than a camera or video input, and the ATEM's model and firmware. A target runs its check on Refresh, whenever the set read from Live changes, whenever a song's time signature arrives or changes while Live is stopped and no Play from start or Count in is starting it, or once Live stops after one did, whenever it comes online, after the producer's pick on its row, and whenever its own file changes at the target, such as a cue recorded, moved or deleted at the lights console; an offline target shows "Not checked." ProPresenter's check says "no playlist picked" until a pick, and "<playlist>: could not be read from ProPresenter" for a picked playlist ProPresenter no longer has, each under "Problems:". Otherwise it lists under "Problems:", in set order, each song whose presentation this Mac is not authorized for ("<song>: not authorized in ProPresenter"), and each song whose playlist item is on an arrangement other than Master ("<song>: arrangement <name> in ProPresenter, not Master"), which triggers nothing, and each song whose presentation ProPresenter would not read ("<song>: presentation could not be read, ProPresenter answered <status>; press Refresh"), which triggers nothing until a Refresh reads it, and under "Cannot match:", in set order, each song with no presentation or playlist item of its name in the picked playlist ("<song>: no presentation or playlist item of its name"), a placeholder or an item ProPresenter has not linked included. A presentation read that ProPresenter answers with a server error, such as a 500 on a cold read, is asked again up to twice, a second apart, before it counts as a read that failed, so a single 500 leaves the song matched. Under "Notes:", in set order, it lists each section of a matched song, Count Off, Pad, Pad Out and End included, with no group of its name, saying what its cue does: "<song>: no group <section>, shows slide 1" before the song's first section with a group, and "<song>: no group <section>, clears" after it, where a group named End matches the End, and so does one named Ending unless the End's cue skips it, after an Ending section of the song's own or a last section that clears. A name that comes both before and after that first section gets one line for each. It also notes, once per name in a song, a name whose count of sections differs from its count of groups ("<song>: <n> sections <name>, <m> groups", such as "Holy Forever: 3 sections Chorus 1, 1 group"), under "Notes:" and never under "Problems:", since a section past the last group of its name triggers that last group. It also notes each section whose group holds more than one slide and more slides than the section has whole bars, when its slides all still fit on beats ("<song>: <section> has <n> slides in <b> bars, changed on beats"), under "Notes:" too, since the server then moves its slides on beats, but not a section whose slide timing entry gives its changes. A section whose group holds more slides than the section has whole beats loses its last slides, since the even split puts them at or past the section's end, so the check lists it under "Problems:" in place of that note ("<song>: <section> has <n> slides in <b> beats, needs a slide timing entry", such as "Ancient Gates: Verse 3 has 3 slides in 2 beats, needs a slide timing entry"), before that song's slide timing problems, but not a section whose slide timing entry gives its changes. Beats do not depend on the time signature, so this problem shows even for a song whose meter is not read yet. The check counts a song's bars with the time signature Live reported while the playhead sat inside that song, never the signature of the song Live sits in now. A song the playhead has not been in since the set was read or the server started is not judged on bars: it gets no "changed on beats" note and no slide timing problem about where a change falls, and the check notes "<song>: meter not read yet" under "Notes:" instead. Walking the playhead through each song before the service fills the check in. It also notes each group with no name whose slides hold words that no section reaches through a slide timing entry's `group` ("<song>: unnamed group <n> (<k> slides), no section shows it", such as Holy Forever's two near its end), under "Notes:", with the position an entry's `group` takes; an entry that reaches it drops the note. Each slide timing entry of a song in the set that breaks one of the file's rules is a problem, after that song's others, naming the song and the entry ("<song>: slide timing <section> <occurrence>, <what is wrong>", such as "Ancient Gates: slide timing Verse 3 1, changes must go up"), and its section keeps the even split and the name match. A title in the slide timing file that matches no song in the set and no presentation in ProPresenter's libraries is a problem too, after the songs' own, as the file spells it ("Holy Forevr: slide timing for no song in the set or in ProPresenter's libraries"), so a typo shows whether or not the song plays this week; an entry of a song outside the set is checked by its title alone, and its entries only once the song is in a set. When ProPresenter's libraries cannot be read, the titles outside the set are one problem, "slide timing <titles>: not checked, ProPresenter's libraries could not be read". A slide timing file the server cannot read, one that is not valid JSON, and one whose top level is not an object of songs is one problem naming the file, last under "Problems:", and no exception applies. It matches a song on the presentation's own name, not the playlist item's, so the item "House of the Lord - [ Full ]" matches the song House of the Lord. Every target matches a name by the same rule, with nothing fuzzier: it compares the names after trimming them, collapsing each run of whitespace to one space, and ignoring letter case. The leader secret never opens the producer page's connection, and the producer secret never opens the leader's. `/producer` alone is the view-only page, and a wrong secret gets its connection refused. The leader page adds the current song's sections as tap targets, and a tap jumps Live there on the next downbeat. It also adds a "Play from start" button and the end toggle's two choices on each song, and beside Play from start a "Count in" button for rehearsal: after a tap on a section while Live is stopped, Count in plays the song's own Count Off, so the band hears its click and the Guide's count, and lands on the tapped section on the bar line where the Count Off ends. Until it lands, every page marks that section as the waiting jump and reads "Count in to" and the section's name. During the count, Stop calls it off and stops Live on the Count Off. A tap on another section of the song changes the section it lands on, and so do Previous and Next, which move one section from that section, never onto the Count Off, a Pad or End; a tap on the Intro lets the count play into it. A tap on another song calls the count-in off and jumps there. On the Count Off or the Intro, Count in does what Play from start does. It is disabled while Live plays, while Live is not connected, with the playhead on a song's End or a Pad, and in a song other than the one the playhead is in. In a song with no Count Off it is disabled and says "No Count Off". The page also adds a Stop button that needs a 1-second press and hold: a bar fills over the hold, and letting go early sends nothing. Beside Stop sits Fade out, enabled while Live plays: a tap fades the music to silence over 6 seconds, and Live plays on with the click and the guide at their level. The button then reads Fade in, and a tap on it fades the music back over 6 seconds. The music also comes back by itself when the playhead reaches the next song's Count Off, from the song before or by "Play from start": it fades in over the Count Off and reaches its level on the song's first downbeat, so the ring of an overlap or a pad under that Count Off comes back gradually. A song with no Count Off gets every volume back at once on its first locator. A tap, Next, Previous or the pedal inside the same song leaves the fade and the silence as they are, and the button is disabled while either fade runs. It fades each group and each track outside a group, except the two tracks named `GUIDE` and `MT CLICK`, where the set builder puts the guide and the click. Live's metronome is not a track, so the click keeps its level whether the metronome or `MT CLICK` plays it. Stop, or Live stopping at a song's End, sets every volume back at once, during a fade or while the music is silent. If the connection to Live drops during a fade or while the music is silent, the server sets every volume back when Live answers again within 10 minutes. After Fade out, the top section carries a second Count in, always there, which counts in to the section the playhead is in by the same rules as the one beside Play from start and says "No Count Off" in the same way; the one beside Play from start stays where it is. After it sits a Play from start, which plays the song the playhead is in from that song's start by the same rules as the one in the song's heading, and is disabled with the playhead in no song, on a song's End or between songs; the ones in the song headings stay where they are. After it sit Previous song and Next song. While Live is stopped, they move the playhead to the first section of the song before or after the one it is in, in set order, so the tap targets show that song's sections and a tap and Count in need no scroll. Nothing plays and no cue fires. Both are disabled while Live plays, a count-in included, and so are they with the playhead in no song and while the server or Live is not connected; Previous song is disabled on the set's first song, and Next song on its last. The section Previous and Next keep what they do. On a phone, Stop, Fade out, Count in, Play from start, Previous song and Next song wrap onto more than one line. Over the tap targets sit Previous, Loop and Next. Loop braces the current section in Live and vamps it until a second press releases it; Next and Previous jump a section on the next downbeat without leaving the song, Next on the last section goes to the song's End, and any jump to another section releases the loop first. A count-in is the exception for its own target: a brace on the tapped section stays on through the count, so the section loops once the count lands, and Loop during the count braces that section, not the Count Off, until a second press releases it. A brace on any other section is released at the press. Every page shows when the loop is on, and which section it holds. Under the tap targets, a Refresh button reads the locators from Live at once, after an edit at the laptop. The server also reads them every 5 seconds while Live is stopped, and never while it plays, so the setlist cannot change mid-song; Refresh is disabled while Live plays. When a read finds the set changed, every page shows the new set, and every song goes back to its default toggle. A read that finds the same set changes nothing.

Do not run the fake Live while Live with AbletonOSC is open, because both use port 11000. To run beside Live, give every program other ports:

```sh
pnpm dev:server --osc-send-port 21000 --osc-receive-port 21001 --http-port 18080
SERVER_HTTP_PORT=18080 pnpm dev:web
```

## Building the Sunday set

`pnpm build-set` builds the Sunday set from the MultiTracks song library: one Live project with the songs end to end in the order named, a 4-bar gap after each by default, and every song's audio copied in. Name the songs in service order:

```sh
pnpm build-set goodness "trust in god" grace
```

A song is any part of its folder name in the library, in any letter case, that names that one folder: `grace` for `This Is Amazing Grace-The Ascension-D-98.00bpm`. A song's whole folder name, in any letter case, names that folder even when longer folder names hold it, as a Finder copy's does. A name that matches no folder stops the build and lists the library's song folders; a name that matches several stops it and lists those. `_template`, `_pads` and a `--pads` folder in the library are never songs.

To see the short names, run `pnpm build-set --list`. It prints each song folder on its own line: a short name that names that one folder, the song's key as its folder name writes it, or `no key`, and the folder name. When the set folder for the date already exists under the output root, a last line after the songs says so, and says whether `--replace` replaces it, in the words `--plan --list` uses; that line never sets exit 1. It reads folder names only and writes nothing, and it takes no song name and no flag but `--library`, `--pads`, `--date`, `--replace` and `--output-root`. It takes `--date`, `--output-root` and `--replace` as the build does, so it looks for the same set folder the build would write, and a `--replace` that names another folder stops it with a usage error, as it stops the build.

To build from the week's Planning Center plan instead, run `pnpm build-set --plan`. It takes the songs from the plan for the set's date, in plan order, and takes no song name. Each plan song's folder is the one whose title, the part of its name before the first hyphen, is the song's title, and whose key is the plan's key for it. A plan key in lower case reads as its note name, `e` as `E`, and a key change as the key before its first hyphen, `G-A` as `G`; a plan key that is still no note name stops the build. The plan gives each song change its transition: an item titled `Prayer` that is the next item after a song, headers left out, puts a pad after that song, and a note on a song whose whole text is `overlap` overlaps it into the next song. Every other song change is a gap, and a transition flag for a song replaces what the plan gives the song change after it.

Check the plan before building it with `pnpm build-set --plan --list`. It prints the set's name, each plan song with its key, its folder or its problem, and the transition after it with where it comes from, then each item that is no song from the first song on with what it does to the set, then a warning for each song whose plan BPM or meter differs from its folder's, then a warning for each song whose arrangement has no chart text in Planning Center, and for each whose chart text has no chords in square brackets, so the chart view would show "No chart for this song" or no chords for it. When no song and no song change has a problem, it runs the build's own checks on the songs' folders, with the template, stem map, transitions and pads folder the build would use, and prints each problem the build would stop on, on stderr after the listing. When the set folder for the date already exists under the output root, a last line says so, and says whether `--replace` replaces it; that line is no problem and never sets exit 1 on its own. It writes nothing, and exits 1 when a song, a song change or the build's checks have a problem. It takes `--template`, `--output-root` and `--replace` as the build does, so it looks for the same set folder the build would write, and a `--replace` that names another folder stops it with a usage error before it asks Planning Center anything. A warning never stops the build.

To type a song's chord chart with headings that match its locators, print its chart skeleton with `pnpm build-set --skeleton <song> ...`, naming the songs as a build does, or `pnpm build-set --plan --skeleton` for the plan's songs in plan order. For each song it prints a line with its number and title, then each locator name of its Live set once, in the order first played, as a heading in upper case, as Planning Center's chord chart asks headings to be typed: `VERSE 1`, `CHORUS`. A blank line comes between songs. Count Off and a locator whose name is blank are left out. A locator name that is no section word (Intro, Verse, Pre-Chorus, Chorus, Bridge, Tag, Interlude, Instrumental, Turnaround, Vamp or Ending) with an optional number, such as Outro, is left out too, and a note on stderr names it; a note never sets exit 1. A song with no folder, one that cannot be read, or one with no locators prints its problem on stderr after every skeleton it could print, and exits 1. It reads the songs' locators only and writes nothing. `--skeleton` takes no flag but `--library` and `--pads`, and `--plan --skeleton` adds `--date`, `--service-type` and `--plan-id`. Pasting the skeleton into Planning Center and typing the chart under it is [in the install doc](docs/install.md#12-typing-a-songs-chart-from-the-skeleton).

`--plan` reads a Planning Center personal access token from `~/.config/setlist-controller/pco.env`, a file only its owner can read. Making it is a one-time step in [the install doc](docs/install.md#8-the-planning-center-token-file). Build from the plan while the Mac is on the internet, before it joins the stage network.

The flags, with their defaults:

- `--date YYYY-MM-DD`: the service date. It defaults to today when today is Sunday, otherwise the coming Sunday.
- `--replace <set folder>`: replaces the set folder for the date when it already exists. Without it, the build stops. Its value is that set folder, `<output root>/<date> <weekday>`, as the last line of `--list` and `--plan --list` prints it, in quotes for its space: `--replace "/Users/nick/Music/Ableton/Sets/2026-11-01 Sunday"`. A `--replace` that names any other folder, or a second `--replace`, is a usage error, so no command replaces a set folder it does not name.
- `--library <folder>`: the song library. It defaults to `~/Music/MultiTracks`.
- `--template <set.als>`: the template project. It defaults to `<library>/_template/template Project/template.als`.
- `--output-root <folder>`: where sets are written. It defaults to `~/Music/Ableton/Sets`.
- `--set-manifest <path>`: the set manifest every build writes for the chart view. It defaults to `~/Library/Application Support/setlist-controller/set-manifest.json`, the file the server reads by default.
- `--show-folder <folder>`: the Eos show folder, where the build finds the template show file and makes the weekly show file. It defaults to `~/Documents/ETC`, Eos's own. The lights step looks there for the weekly show file.
- `--lights`: runs the lights step for the set built for the date, and builds nothing: it labels each song cue of the weekly show file open in Eos with its song's title, gives the colour lights in it the colour of the song's ProPresenter background, and saves the show. It takes no song name, and no flag but `--date`, `--output-root`, `--show-folder`, `--connections-config` and `--playlist`.
- `--connections-config <path>`: the connections config, for `--lights`, which reads Eos's address and cue list from its `eos` section and ProPresenter's address from its `propresenter` section. It defaults to `~/Library/Application Support/setlist-controller/connections.json`, the file the server reads by default.
- `--playlist <name>`: the ProPresenter playlist the lights step takes the songs' colours from, for `--lights`, by its whole name, trimmed, with each run of spaces as one, in any letter case. Without it, the playlist is the one whose name holds the date of the set. Give it when the lights step says that no playlist carries the date, or that more than one does.
- `--pads <folder>`: the pad files, one WAV per key named by its key, such as `A.wav`. It defaults to `<library>/_pads`.
- `--overlap <n>`: overlaps song `n` into the next one, so the next song's Count Off starts on song `n`'s Ending, where its click and guide stop, and its other stems ring on and fade out. `n` counts the songs from 1. Give it once for each song to overlap.
- `--pad <n>`: puts a pad after song `n`, in the next song's key, on the template's PAD track, and the next song's Count Off starts at its end. `--pad <n>=<key>` gives the pad its own key instead, such as `--pad 2=G`. A pad may follow the last song. Give it once for each pad.
- `--gap <n>`: makes the song change after song `n` a gap, to take back a pad or an overlap the plan gives it. Without `--plan` it changes nothing.
- `--service-type <name or id>`: the plan's service type, by its name or its id, for `--plan`. It defaults to `Service`.
- `--plan-id <id>`: the plan, by its id, for `--plan`, when the service type has more than one plan on the date.

One song change takes one transition: a gap, `--overlap` or `--pad`. The usage text, which `pnpm build-set` prints with no song named, gives the fade lengths, the key names a pad takes, and what a pad after the last song does. A relative path in a flag resolves from the folder the command runs in.

The set is written to `<output root>/<date> <weekday>/<date> <weekday>.als`, such as `~/Music/Ableton/Sets/2026-10-18 Sunday/2026-10-18 Sunday.als`. Each song's audio is copied into `Songs/<title>/` beside it, and the pad files into `Songs/_pads/`. The command then prints its summary, the set's name, one line per song, and the set's path last, to check before opening the set in Live:

```
<date> <weekday>
<n>. <title>  bar <start bar>  <tempo> BPM  <meter>  <transition>
<path to the set>
```

A song's line ends with the transition after it, `gap`, `overlap` or `pad in <key>`, when one follows it.

Every build also writes the set manifest, replacing the last one, so the chart view on the band's phones shows this week's charts: each song's title, the key of its stems from its folder name, its starting meter, which the chart view counts the bars of every block but the current one in, and, with `--plan`, the chart key and chart text of its arrangement in Planning Center. A build by song names writes no chart key and no chart text, so last week's charts never show on this week's set. A build with a problem writes no manifest. When the set is built but the manifest cannot be written, the command prints the summary, then one line on stderr naming the manifest, and exits 1; the chart view keeps the last manifest's charts until a build writes a new one. Neither chart warning of `--plan --list` stops the build or sets exit 1.

After the set, every build makes the weekly show file for the lights: a copy of the newest template show file in the show folder, named `<weekly show name prefix> <date> <time of the copy>.esf3d`, such as `Church Sunday 2026-10-18 2026-10-15 20-04-09.esf3d`. Eos names each save of a show `<show name> <YYYY-MM-DD HH-MM-SS>.esf3d` and keeps every save as its own file, so the newest template show file is the file of the template show name with the latest time in its name. After the summary, the build prints the path of the weekly show file and the three steps that open it in ETCnomad: File, Open; the file; OK.

```
Weekly show file: <show folder>/<weekly show name prefix> <date> <time of the copy>.esf3d
Open it in ETCnomad: File, Open; <weekly show name prefix> <date> <time of the copy>.esf3d; OK.
```

With no template show file in the show folder, or no show folder, the set is still built and the command exits 0, and one line after the summary says so: `The lights step is not done: no template show file named "Church Sunday template" was found in <show folder>.` The build never replaces or deletes a file in the show folder: a rebuild with `--replace` makes a newer weekly show file from the newest template show file and leaves the older one in place. A build with a problem makes no weekly show file, and neither do `--list`, `--plan --list` and `--skeleton`, which take no `--show-folder`. When the set is built but the show folder cannot be read, or the copy fails, the command prints the summary, then one line on stderr naming the show folder and the cause, and exits 1. The build talks to no Eos.

Once the weekly show file is open in ETCnomad, run the lights step for the same date: `pnpm build-set --lights`. It builds nothing. It reads the songs, in order, from the set built for the date under the output root, and Eos's address and cue list from the `eos` section, and ProPresenter's address from the `propresenter` section, of the connections config, the file the server reads. It writes to Eos only when the show open in Eos is the newest weekly show file for the date in the show folder, and only while the command line reads LIVE. Then it labels each song cue with its song's title, as the set holds it, records the song's colour into the cue and into each cue of its chain on the colour channels, records the colour each cue straight after one of a song's cues had back into that cue, since a colour tracks into the cues after it, saves the show as Shift and Update save it at the keypad, and prints one line per song, then one line for each cue of a chain, then one line for each cue it copied, and one more when a follow or a hang was taken off the copy, then one warning line for each colour channel at intensity 0 in a song cue, and, last, the path of the show file the save made:

```
<n>. <title>  cue <cue list>/<cue>  hue <hue>, red <red> green <green> blue <blue>  <background file>
<n>. <title>  cue <cue list>/<cue>  template colour  <why>
Cue <cue list>/<cue> is in the chain of cue <cue list>/<cue> (song <n>, <title>), and is coloured as that song is.
Cue <cue list>/<cue> (song <n>, <title>) is a copy of cue <cue list>/<cue> (song <n>, <title>).
Cue <cue list>/<cue> does not keep the follow of cue <cue list>/<cue>: the lights step took it off.
Warning: channel <channel> is at intensity 0 in cue <cue list>/<cue> (song <n>, <title>), so the song's colour will not show on it.
<show folder>/<weekly show name prefix> <date> <time of the save>.esf3d
```

Song `n`'s cue is the first cue of the cue list whose label is the lights config's `songCueLabel` for `n`, `Song 1` for `Song {n}`, trimmed, with each run of spaces as one, in any letter case, or, with none, the first cue labelled with the song's title, as a run before this one left it.

A song owns its chain: every cue its song cue runs on into by a follow or a hang, cue after cue, by its link or with none into the next cue of the cue list. A link with no follow and no hang runs on into nothing. Each cue of a song's chain takes the song's colour and keeps its label, and the summary names each one with its song. For a song that keeps the template's colour, each cue of its chain keeps the colour it had. Each cue no chain holds that stands straight after one of a song's cues gets the colour it had recorded back into it, so a cue no chain reaches keeps the template's colour, wherever it stands in the cue list. A chain that runs on into another song's cue, into a cue of another song's chain, or by a link to no cue of the cue list stops the lights step before anything is written.

A set with more songs than the cue list has song cues gets, for each song after the last that has one, a copy of that song's cue, made with Copy To before anything else is written, numbered after that cue and every cue of its chain, and before the next cue: the next whole number when it is free, otherwise a decimal between the two. A follow or a hang Eos copies with the cue is taken off the copy, so the copy runs on into nothing, and the summary says so in a line after the line of the copy: `the follow`, `the hang`, or `the follow and the hang` with `took them off`. The copy then takes its own song's title and colour like any song cue, and the summary names each copy and the cue it is a copy of. A set with fewer songs leaves the other song cues as they are, `Song n` label included. A second run on the same weekly show file copies nothing and leaves the show as the first did.

Song `n`'s colour comes from the one ProPresenter playlist whose name holds the date of the set, written as `November 15, 2026`, or with `--playlist <name>` from the one playlist of that whole name, by the same rule: from the picture of the first cue of the song's presentation in it: the first presentation it links whose own name is the song's title, by the same rule, or, with none, the first whose playlist item's name is the song's title, less a Planning Center arrangement such as ` - [ Full ]`. A presentation whose own name is not the song's title, as a Planning Center import names one for its recording, `<title> (Live)`, matches once its playlist item is renamed to the song's title in ProPresenter. With no playlist for the date or more than one, or with `--playlist` and no playlist of that name or more than one, nothing is written to Eos, the playlists it could mean are printed, one a line, each as `--playlist "<name>"`, and one line on stderr says why, exit 1. The colour is the hue of the most saturated of the picture's large areas that are not near black, never its mean, at the lights config's `saturation` and full brightness, and each song's line shows it as hue and as red, green and blue percentages, with the background file it came from, the label of the presentation's first slide.

There is no picture when it has no opaque pixel, when it has no large area that is not near black, when the most saturated of those areas is under 5% saturation, as ProPresenter's grey placeholder and a slide with no background are, when ProPresenter refuses it, or when it cannot be read. ProPresenter gives the placeholder for a picture it has not drawn yet, so the mode asks for a picture it did not get again, once a second, up to 5 times, and takes the first it gets. A song that still has no picture, and a song with no presentation or playlist item of its name in the playlist, keeps the template's colour: on each colour channel the colour its song cue had, recorded into the cue so the colour of the song before it does not track into it. Its line shows `template colour` and why: `no picture, <background file>`, `ProPresenter refused the picture (<status>), <background file>`, `the picture cannot be read, <background file>`, or `no presentation or playlist item of its name in the playlist "<playlist>"`, which also names each presentation of the playlist that ProPresenter did not give. Such a song takes about 5 seconds longer. A colour channel at intensity 0 in a song cue shows no colour there, so the summary warns of each one. A warning never stops the run and never sets exit 1.

Eos is sent the colour through each channel's red, green and blue parameters, and it is recorded with Record Only, confirmed when Eos asks. The lights step sets no intensity and no channel but the colour channels. When it is not done, one line on stderr says why and the command exits 1. Nothing is written to Eos with no set built for the date, a connections config that names no Eos or no ProPresenter, Eos or ProPresenter not answering, another show open in Eos, a command line that does not read LIVE, no cue for song 1 or for a song before one that has a cue, a chain that runs on into another song's cue, into a cue of another song's chain or by a link to no cue of the cue list, no cue number free for a copy, or a playlist the mode cannot choose. With another show open, the command also prints the weekly show file and the three steps that open it. With no weekly show file for the date, it makes one from the template show file, as a build does, prints it with the three steps, and stops there, since a file made just now is not the show open in Eos. When Eos sends no saved event, the song cues are labelled and coloured in the open show, and the line says to save the show by hand. When the run stops after it began to write, the line says that the open show is changed and not saved: open the weekly show file again without saving, then run the lights step again. `--lights` takes no song name, and `--connections-config` or `--playlist` on a build is a usage error.

When the build's checks find a problem, it prints each problem on its own line on stderr, exits 1, and writes nothing. An error during the build also prints one line and exits 1. A usage error, such as no song named or a `--date` that is not a real date, prints the problem and the usage text and exits 2.

Every build also writes a `set-recipe.json` file beside the built `.als` recording the resolved song list, transitions, paths, and optional plan and lighting settings. To change one song in an already-built set without rebuilding from scratch or losing rehearsal edits saved in Live, close the set in Live and run `pnpm build-set edit` on the set folder (or with `--date` and `--output-root`):

- `--swap <song> <replacement>`: replaces `<song>` (by 1-based position or song name) with `<replacement>` from the library.
- `--add <song>` with optional `--at <pos>`: inserts `<song>` at position `<pos>` (or appends it at the end when `--at` is omitted).
- `--drop <song>`: removes `<song>` from the set.

`pnpm build-set edit` reads the existing `.als` first to carry every untouched song's locators as Live has them, renamed and added ones included, and its track mixer volumes and clip gains, atomically re-materializes the set with APFS clones, updates `set-manifest.json` (preserving Planning Center charts on untouched songs so connected band devices reload automatically), updates any pad files, and regenerates Eos lighting cues when `--lights` was run on the set. Any validation error leaves the existing `.als` and `set-manifest.json` untouched.

The build expects four things:

- Every song saved in Live 12. A song saved by an older Live stops the build: open it in Live 12 and save it, then build again.
- The template project in the library, at `_template/template Project/template.als` (setlist-controller#33). A build with a pad needs an audio track named `PAD` in it, outside every group.
- The stem map at `config/stem-map.json` in this repository, which puts each MultiTracks stem name under the template group or track it plays in. A song with a stem the map does not list stops the build; add the new stem name under its group there. A stem map that is missing or is not valid JSON, such as one with a comma after its last entry, stops the build with one line that names `config/stem-map.json`. A stem map with the wrong shape stops the build the same way: a top level that is not an object, or a group whose stems are not a list of stem names in brackets, such as `"VOX": "BGVS"` for `"VOX": ["BGVS"]`. For a group, the line names the group too.
- The lights config at `config/lights.json` in this repository, which gives the template show file's show name as `templateShowName`, the start of each weekly show file's name as `weeklyShowNamePrefix`, and the label of a song cue as `songCueLabel`, with `{n}` where the number of the song goes, such as `Song {n}`. It also gives the channels of the colour lights as `colourChannels`, such as `[1, 2, 3, 16, 17, 18]`, and the saturation they take a song's hue at as `saturation`, a number from 0 to 100. A lights config that is missing or is not valid JSON stops the build with one line that names `config/lights.json`, before anything is written. One with the wrong shape stops the build the same way: a top level that is not an object, a name that is missing, is not in quotes, is empty or holds a `/`, a `songCueLabel` that is missing, is not in quotes or holds no `{n}`, `colourChannels` that are missing, empty, or anything but a list of whole numbers from 1 with none twice, or a `saturation` that is missing or is no number from 0 to 100. It stops the lights step the same way.
